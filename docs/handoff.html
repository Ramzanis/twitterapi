Skylark — a metered X data API

Customers call our endpoints with an API key. We serve from cache or fetch from an upstream scraper, return the data, meter the call, and bill it against a credit balance. This is what exists, why it's shaped this way, and what will bite you.

The shape of it

Two programs, two repositories, one dependency between them.

twitterapi

The product: landing page, Google sign-in, customer dashboard, staff console, and the metered API itself. Runs on :3000.

skylark-mock-provider

A sibling directory standing in for the paid scraper. Real HTTP, auth, pagination, rate limits, injectable faults. Zero dependencies. Runs on :4000.

The provider is deliberately a separate process, not an in-process stub. That means the client code exercises real request building, timeouts, retries and error classification — so pointing at a paid scraper is a base URL and a key, not a rewrite. If it isn't running, the API returns 502. That's correct.

One request, end to end

1Hash the X-API-Key, look it up → org, plan, status
2Rate limit, then credit balance → 429 / 402 if exceeded, both logged
3Look up response_cache by params hash → hit: serve immediately
4Miss: write a fetch_jobs row, call the provider over HTTP → retry, then cache
5Write api_requests + debit credit_ledger → same transaction, always
The cache is the business model

A cache hit costs nothing upstream but still bills the customer — measured at roughly 7× faster than a miss. That gap between the $0.15 charged and the ~$0.03 paid upstream is the margin, and the cache is what widens it. It is keyed by query alone, so it is shared across organizations: one customer's search warms it for the next.

Running it

Three terminals. Everything is local — no cloud account, no payment provider, no traffic to X.

# 1 — database
pnpm db:up            # Postgres 17 in Docker
pnpm db:migrate       # apply db/migrations/*.sql

# 2 — upstream data provider (separate directory)
cd ../skylark-mock-provider && node server.js

# 3 — the app
pnpm dev              # http://localhost:3000

Sign in at /signin. Without Google credentials configured, dev builds offer a local email login that runs the identical provisioning path — first sign-in creates the user, a personal organization on the free plan, an owner membership and a $0.10 signup bonus, in one transaction. Production refuses to register that login at all.

Then create an API key on the dashboard (shown once), and pnpm staff you@example.com to reach the admin console at /admin.

Where things live

Two organising ideas: config that changes rarely lives in code, and components are grouped by who looks at them.

app/
  dashboard/          customer area — usage, billing, payment-methods, account
  admin/              staff console (+ orgs/[id])
  api/
    x/tweet/search/   the metered endpoint
    webhooks/[provider]/   payment gateway callback
    cron/reconcile-topups/ safety net for lost webhooks
    usage/export/     CSV
components/  ui · marketing · dashboard · admin
config/      plans · pricing · providers · billing   ← config as code, not tables
lib/         apiAuth · authz · ledger · billing · usage · admin · rateLimit
             providers/{client,tweets} · payments/gateway
db/          schema.ts · migrations/ · index.ts
scripts/     seed · make-staff · verify-ledger · verify-topup

Plans, endpoint pricing and the provider catalog are TypeScript, not database rows. They change rarely, have no runtime state, and get free versioning and code review through git. What was actually charged is still recorded on every api_requests row, so history survives a price change. Promote any of them to a table the day you need to edit it at runtime.

Data model

Eleven tables. Everything hangs off an organization, never a user.

TableHolds
usersKeyed on Google's stable subject id, not email. Soft-deleted.
organizationsPlan, status, billing identity, spend caps, alert memory. The billing unit.
organization_membersowner / admin / member
api_keysSHA-256 hash plus a display prefix. Live or test.
credit_ledgerAppend-only. The source of truth for balance.
api_requestsOne row per call, including rejected ones at zero cost.
fetch_jobsOne row per upstream call. Attempts, cost, failure kind.
response_cacheKeyed by params hash. The margin lever.
topup_requestsCustomer asks to add credits; staff or a webhook fulfils.
webhook_eventsEvery gateway delivery, for dedupe and for disputes.
audit_logsOne generic activity table. Null actor means a system action.

Every user gets a personal organization at signup, even alone. Retrofitting that with live customers is painful; starting with it costs one extra table and makes the Teams plan a matter of adding members.

Migrations

db/schema.ts is the source of truth. Generate with an explicit name — pnpm db:generate --name=what_it_does — then read the SQL before committing. Generated SQL adds columns but never knows how to fill them: 0001_credit_buckets_and_alerts.sql carries a hand-written backfill that classifies existing ledger rows and recomputes running balances per bucket. Renaming a migration is safe if you also update its tag in meta/_journal.json — the applied table keys on a hash of file contents, not the filename. Never run db:push against real data.

Money invariants

If you change one thing carelessly, make it not be one of these.

Balance is derived, never stored

There is no mutable balance column. The balance is the newest ledger row per (org, bucket), summed. Every write locks the organization row first, so concurrent debits cannot compute the same balance_after. Ten simultaneous debits have been tested: exact totals, no lost updates.

A payment credits exactly once — enforced three ways

The gateway's event id is unique on webhook_events and recorded before any crediting. Fulfilment matches only pending or processing rows. And credit_ledger.source_id carries a partial unique index, so a second credit for the same top-up is rejected by Postgres regardless of application bugs. Two concurrent "mark paid" calls have been tested: one credits, one returns null.

Credit what was captured, not what was requested

amount_cents is the customer's wish; amount_received_cents is the gateway's fact, and it is what reaches the ledger. They diverge on currency conversion, fees deducted at source, and customers transferring a different number.

The browser never moves money

A success redirect is a UX cue. Only a signature-verified server-to-server webhook — or a human matching a bank reference — may credit. With no gateway configured, the webhook route returns 503 and credits nothing, which is the safe default.

Upstream failure is never the customer's bill

A 502 is logged to api_requests at zero credits and the balance is untouched. Meanwhile upstream_cost_micros records every attempt including retries, because retries genuinely cost us — which keeps the admin margin figure honest.

Two credit buckets

Paid credits are deferred revenue and a real liability; bonus credits are marketing spend with no cost basis. They are separate chains, consumed bonus-first, and a charge that straddles both writes one row per bucket sharing the request id.

Verifying it works

Two scripts cover the parts where a bug costs real money.

npx tsx scripts/verify-ledger.ts   # balance chain + 10 concurrent debits
npx tsx scripts/verify-topup.ts    # exactly-once fulfilment + partial capture

They assert, rather than print and hope: totals are exact, every (bucket, balance) pair is distinct, each chain reconciles against the sum of its amounts, two simultaneous fulfilments credit once, and $50 requested with $48.70 captured credits $48.70.

Provoking failure

Restart the provider in a fault mode and call the API — these paths are otherwise untestable:

cd ../skylark-mock-provider
npm run flaky                          # 30% fail  → retries, 502, no charge
FAIL_RATE=1 node server.js             # always fails → fetch_jobs = failed, 3 attempts
BASE_LATENCY_MS=9000 node server.js    # slower than timeout → timed_out

Per-request faults work too: _fail, _status, _latency, _hang, _truncate, _empty. See that project's README.

Traps

Things that cost time to discover once already.

  • Server actions can't be driven by curl. Next expects React Flight encoding, so Roll/Revoke, the account forms and admin controls need a real browser click. Their underlying functions are tested directly instead — that's why fulfilment logic lives in lib/billing.ts rather than inside the action.
  • Format money as en-US explicitly. A Norwegian server locale rendered a balance as $4,00. Counts can follow the viewer; currency cannot.
  • Timestamps must render client-side. Server components format in the server's zone, which is UTC in production. LocalTime renders UTC then swaps after hydration.
  • Clever SQL through the ORM is where this codebase breaks. Drizzle renders a column reference inside sql without its table prefix, producing an ambiguous bare "id"; and parameterised intervals fail type inference. Both were fixed by replacing one clever query with several flat ones.
  • A long-lived dev server goes stale. After heavy edits and a database wipe, every API call returned 500 while a fresh production build of the same code returned 200. Restart before debugging a ghost.
  • The response cache is global. Cache-hit rate is a property of total traffic, not per-customer traffic. Don't read it as a customer-level metric.

The governing principle

Design the schema for the end state, because it is expensive to change with live customers. Deploy the infrastructure for the current one, because that is cheap to change. Everything above slots in without touching the eleven tables.
