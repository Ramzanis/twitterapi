Skylark · architecture

How the whole system fits together

Customers call a metered API with an API key. Every call is authenticated, rate-limited, checked against the credit balance, served from cache or fetched from the upstream provider, then logged and billed in one database transaction. The WebSocket stream delivers posts live, billed the same way. The only incoming webhook is the payment provider's.

1. Processes and how they talk

Three programs run locally: the Next.js app, the realtime server, and Driftnet (the mock data provider, in a separate repo). All state is in one Postgres database.

Why two Skylark processes

Next.js route handlers can't hold a socket open open, so the WebSocket gateway lives in server/stream.ts.

Swapping the provider

All upstream calls go through lib/providers/. A paid scraper means a new PROVIDER_BASE_URL and key, plus response mapping if its shape differs.

Single instance for now

The rate limiter and stream connection counts are in-process. Running two copies needs Redis first.

2. One metered REST call

All 13 data endpoints run this same pipeline, in lib/meteredEndpoint.ts. Each route file only validates its parameters and names a provider call.

sequenceDiagram
  autonumber
  participant C as Customer
  participant R as Route /api/x/…
  participant M as serveMetered()
  participant DB as Postgres
  participant P as Driftnet

  C->>R: GET /api/x/user/profile?username=… (X-API-Key)
  R->>M: endpoint, parse(), fetch()
  M->>DB: look up SHA-256(key) → org, plan
  Note over M: 401 bad key · 403 suspended org
  M->>M: validate params (400, not logged)
  M->>M: rate limit per key (429, logged at $0)
  M->>DB: balance ≥ price? (402, logged at $0)
  M->>DB: response_cache hit?
  alt cache hit
    DB-->>M: payload (costs us nothing, still billed)
  else miss
    M->>DB: insert fetch_jobs (running)
    M->>P: HTTP with timeout, retries, backoff
    P-->>M: data, or 404 / failure
    M->>DB: cache payload · fetch_jobs succeeded, cost × attempts
    Note over M: upstream failure → 502, 404 → 404, both $0
  end
  M->>DB: ONE transaction: insert api_requests + debit credit_ledger
  M-->>C: { data, meta: cache_hit, credits_charged, balance, latency }

3. The stream

Customers write stream rules (topics), hold one WebSocket, and receive matching posts. Each post is billed as it is delivered; backfill covers anything missed while disconnected.

Nothing is skipped

If the upstream socket drops, the gateway reconnects and seeks back to the last post it delivered.

Catching up

After a customer disconnects, backfill returns what their rule matched since their last cursor (Driftnet keeps nearly three hours).

Plan limits

Rules and concurrent connections are capped per plan: maxStreamRules, maxStreamConnections.

4. How money moves

The balance is never stored. It is the newest ledger row per bucket, and every writer locks the organization row first.

5. Data model

Twelve tables, defined in db/schema.ts. Everything belongs to an organization, never to a user. Plans, prices and providers are config in code, not tables.

webhook_events (incoming payment-provider webhooks) and response_cache (shared across organizations) stand alone.
